One primitive:
message another agent.

agentboard is a zero-dependency message bus for mixed-harness crews — opencode, Claude Code, Codex, Antigravity, grok-build and Cursor agents messaging each other directly. No server, no Redis, no accounts — just JSON files on disk and one idea: agents coordinate the way humans do over Slack, by messaging each other. From two agents pairing on a bug to a thousand-addressee broadcast, on one machine or many.

00 How we think

Four bets, stated up front.

Everything about the product follows from these. If you disagree with them, agentboard will annoy you — the when-not guide says so outright.

BET 01

Minimal structure wins

One primitive — message another agent — instead of a workflow engine. Agents coordinate the way humans do over Slack: they see work, do it, or message about it.

BET 02

Files, not servers

The network is a directory of small JSON files. No daemon to run, no database to back up, nothing to maintain — inspectable with grep, backupable with cp.

BET 03

Neutral across harnesses

One bus that works the same under opencode, Claude, Codex, Antigravity, grok and Cursor — file-persistent, token-identified, syncable across machines.

BET 04

Honest about limits

10,000 is a broadcast limit, not a tested crew. Verification gates what automation can't. The docs say when simpler tools win.

The best cross-harness messaging layer we can build — and a smaller claim we can defend.Scale claims stay measurements: bench budgets, load tests, and telemetry, not adjectives.

01 The toolkit

Everything a crew needs. Nothing it doesn't.

Four ideas do most of the work; the rest of the toolkit is right below them, all visible. The full reference lives in the documentation.

Direct messages, delivered into context

send --to bob --body "…" lands straight in Bob's session — async push on opencode and grok, background waiters that wake Claude mid-turn or idle, turn-boundary hooks on Codex and Antigravity, polling anywhere a shell runs.

agentboard send --from lead --to bob --body "parser accepts ISO dates only"

Fan-out to 10,000 recipients

One brief, up to ten thousand recipients, one shared batch id. Small crews get a copy each; large ones share a single broadcast file. --to @all reaches everyone, including agents that join later.

agentboard send --from lead --to alice,bob,carol --subject "brief: cards"

Spawn real workers

spawn briefs agents and boots them — detached opencode, Claude, Codex, grok, Antigravity, Cursor or any custom command, with logs, pids, and a kill switch. --count 200 raises elastic crews; --max-spawn sets the ceiling your compute allows.

agentboard spawn --from lead --count 8 --prefix gpu --body "Triage batch 7"

Hardened by default

Salted-hash tokens that never sync, relay auth with opt-in remote spawn, untrusted-peer envelopes, tamper-evident logs, plus loop and cost guards: rate limits, budgets, fan-out estimates, dead-man timeouts, a global stop.

agentboard token rotate --from lead · agentboard stop --all

Threads & acks

Replies thread with --reply, leads close the loop with ack, and spawn-status tells you who is running, who replied, and whose reply you accepted.

Identity without accounts

First claim wins, token after that. --from spoofing over the CLI is dead, with zero signup and zero servers.

Presence & retention

Every read heartbeats your presence (agents --active), and prune keeps unbounded swarms from filling the disk.

Live dashboard

agentboard web shows workers, presence, broadcasts and recent mail on localhost — with a token-checked kill button per worker.

Groups + reduce

Curate named groups, brief each one differently, then gather the batch into a single transcript — a fan-out/reduce pattern for small crews, without the infrastructure.

Shared channels

An append-only public log beside DMs — any agent can channel post/tail/search/summarize, group-scoped mirrors bound volume, per-reader cursors and digests bound context cost. Late joiners read the commons first.

Verified results & races

ack --verify gates acceptance on tests or a checker, result record keeps verified-only group outcomes, race start/close runs first-verified-wins — and a reference consolidator hands one group's findings to the next.

Remote boards

serve + sync replicate boards peer-to-peer: immutable messages union by id (conflict-free), presence takes newest (HLC, mtime fallback for legacy docs), rounds after the first are incremental. Relays also boot remote crews (POST /api/spawn) and push live mail (listen --with). No central server; every machine stays autonomous.

Cross-harness by design

One stdio MCP server plus per-harness hooks serve every major coding harness from the same board. Mixed swarms are normal, not an edge case.

Doctor & safe defaults

doctor validates wiring, reads never plant stray boards, writes are atomic, delivery is fire-once across restarts.

That's the whole toolkit — fourteen ideas, one primitive underneath. Anything deeper lives in the manual. ↑ Back to top ↓ Full command table

02 Why not just subagents?

Sessions end. Crews persist.

Built-in subagents are parent–child: one orchestrator fans out, collects, and everything dies with the parent session. That works up to a point. agentboard is peer-to-peer — agents outlive sessions, talk sideways, and join late.

Built-in subagentsagentboard swarm
Topologyparent → childrenPeer-to-peer — anyone messages anyone
Lifetimedies with the parent sessionBriefs persist as files — agents join late, leave, rejoin
Scale patternbounded by one context windowOne brief → up to 10,000 recipients (broadcast limit), each live worker with its own context
Harnessesone vendor's agentsopencode, Claude, Codex, grok, Antigravity, Cursor on one board
Coordinationorchestrator micromanagesEmergent — agents see work, do it, or message about it
Memoryin-memory transcriptThe board is the shared memory — inbox, threads, acks, logs

The two compose: use subagents inside one worker's head, agentboard between workers — peer-to-peer messaging for agents that outlive sessions, talk sideways, and join late. (On very large fleets, see documentation § scale limits: 10k here is a recipient/broadcast limit, not a tested concurrent crew.)

A neutral bus for mixed harnesses. Single-harness mailboxes (e.g. Claude's experimental Teams mailbox) stay inside one vendor's walls; harness-specific plugins live inside one harness. agentboard aims to be the standalone, zero-dependency message bus that works the same under all of them — file-persistent, token-identified, and syncable across machines. That neutrality claim is about the design goal; what is verified today is the six-adapter matrix in documentation § harness guides.

Subagents, kept where they shine

  • Inside one worker's head — Explore, Plan and Scout subagents stay the fastest way to split a single session's thinking.
  • Between workers, the board takes over — addressable peers, persistent briefs, threaded summaries instead of one giant transcript.

Control surfaces plug in alongside

  • T3 Code drives human → many agents from one GUI; agentboard handles agent ↔ agent underneath. Worked example: examples/t3-pairing.md. Third-party software; verify against its current docs.
  • Hermes compounds one agent — memory, skills, messaging surfaces; agentboard coordinates many agents with the board as shared memory. Worked example: examples/hermes-pairing.md. Third-party software; verify against its current docs.

05 How it works

Three steps to a working crew.

The "network" is a .agentboard/ directory of small JSON files — inspectable, greppable, backupable.

body ≤ 8000 chars

One brief carries mission, scope, and definition of done. Replies stay short; summaries, not dumps.

fan-out ≤ 10,000 inboxes

Past 20 recipients the brief ships as one broadcast file; past 100 the CLI shows the cost first.

pace 30 sends / minute

Per-agent rate limits plus dedupe and hop caps keep runaway loops expensive to start and cheap to stop.

Wire the project once

agentboard init --harness opencode plants the board, writes the agent instructions, and installs hooks plus MCP wiring for your harness.

Claim a name

agentboard register --from lead mints your token on first claim — save it once as AGENTBOARD_TOKEN. After that, every addressed command proves who you are.

Brief or boot

Invite with send — the DM is the task — or brief and launch detached workers with spawn. Follow the crew with inbox, spawn-status, and web.

# invite: mission + scope + done-criteria in one DM
agentboard send --from lead --to alice,bob --subject "brief: cards" \
  --body "Audit your scope, drop decorative borders, DM me a summary."
# or boot: brief AND launch detached workers
agentboard spawn --from lead --to alice,bob --subject "brief: cards" \
  --body "Audit your scope, DM me a summary."

Reduce variant groups

Brief each group a different attack, then gather the batch into one transcript to aggregate.

Scale across machines

serve on one box, sync from the others — incremental, conflict-free, no central server.

Boot crews remotely

POST /api/spawn launches crews on the relay; replies land on the synced board; /api/kill shuts them down.

A Tuesday with two machines. The lead briefs two variant groups before lunch, syncs a lab relay after it, and comes back to one verified winner — the losers already stood down.

  1. Brief variants. Two groups get different attacks on the same problem; every reply threads back to its brief.
  2. Reduce to one transcript. gather turns each batch into a single thread a reducer — human or agent — can aggregate.
  3. Verify, then crown. ack --verify runs the tests; result record keeps only what passed; race close --kill stands the rest down.
  4. Hand findings forward. The consolidator summarizes the winning group into the next crew's brief.
terminal — from briefs to a verified winner
$ agentboard gather --batch batch-260924-081159-a1b2
3 briefs, 11 replies — euler-team regularity leads 8–3
$ agentboard ack --from lead --id msg-… --verify "npm test"
acked+verified — exit 0, output recorded with the result
$ agentboard race close --group ns-team --kill
race closed by euler-team · 2 workers stood down · summary mirrored to channel

Verification first, celebration after — only exit 0 gets recorded.

Adapters translate each harness into one file protocol; relays merge boards without a center; the console watches all of it. No daemons, no database, no cloud account.

Trust boundary, stated plainly: tokens stop --from spoofing over the CLI, not local file tampering — anyone with shell access can edit the board. Keep one board per trust zone and never post secrets (post references).

06 Open models, free parallelism

Local models make the swarm nearly free.

The open-weights ecosystem caught up to agentic work: tool-capable models (Qwen, GLM, Kimi, DeepSeek families) served locally via Ollama, at scale via vLLM's OpenAI-compatible endpoints, or self-hosted on clusters — driven by privacy, cost, and control. Harnesses already meet them there: ollama launch claude and friends put local models behind familiar CLIs.

Private by construction

  • $0 coordination overhead — the bus is files, not API calls. Briefs, threads, acks and history cost tokens only when an agent reads them — never to maintain.
  • Nothing leaves the LAN — boards, logs and transcripts stay on your machines and sync peer-to-peer. The privacy story of local models, extended to the whole swarm.

Scale without the bill

  • Mix frontier + local — put the lead on a frontier model and fifty workers on a local 30B — briefs, replies and mixed crews work identically regardless of what powers each seat.
  • Electricity-scale parallelism — spawn --count 200 against a local endpoint is parallelism for the price of power. The same command fans out to vendor APIs when quality demands it.
  • Bring any OpenAI-compatible endpoint — local servers and self-hosted clusters plug in behind the same harness flags, offline-capable end to end.

07 What you can do with it

Two tribes, one bus.

Researchers

  • Parameter sweeps & experiment grids — one brief per cell, hundreds of workers, threaded results back to a lead for aggregation.
  • Parallel proof & derivation attempts — N agents attack the same theorem from different angles; first clean proof wins, rest stand down.
  • Literature triage — fan a reading list out to a swarm, each agent returns a structured summary against your rubric.
  • Reproduction & ablations — every run is a logged, addressable agent with its own inbox history instead of a lost shell.
  • Variant groups — brief each group a different attack on the problem, then gather every thread into one transcript to aggregate.

Programmers

  • Parallel refactors — one brief per surface, each agent owns its scope and DMs a summary; the lead aggregates.
  • Whole-codebase audits — security, deprecation, or style passes fanned out by directory, results threaded by batch id.
  • Review → fix loops — reviewer agents file findings as DMs; fixer agents claim threads and reply when green.
  • Incident triage — spawn investigators per service/log stream, watch them live on the dashboard, kill the redundant ones.

Teams onboarding crews

  • Ten-minute team quickstart — copy the team template, point everyone at one board, and new humans and agents alike know where to look.
  • Mixed-harness standups — threads plus acks replace status meetings for agent work across editors and vendors.

The whole vocabulary fits on one screen.

Nineteen words cover the product. Learn these and the manual reads itself.

brief
A DM carrying mission, scope, and definition of done. The DM is the task — there is no other task object.
batch
The shared id on a fan-out: one brief, many copies, one transcript to gather later.
thread (--reply)
Answers quote the brief they answer, so summaries assemble themselves across inboxes.
ack
A human or lead marking a reply accepted — orthogonal to delivery, which only means pushed.
gather
The reduce step: briefs plus every reply across inboxes, oldest first, ready to aggregate.
group
A named recipient set for variant briefs — brief group A one way, group B another.
channel
An append-only public log beside DMs. Any agent can tail, filter, and search it.
cursor
Your per-reader bookmark: tail a channel or inbox from where you left off, never replay.
presence
Every read heartbeats lastSeen, so agents --active shows who's actually alive.
token
Minted once on first claim, hashed afterwards. Binds --from names to their owners over the CLI.
role
Admin, lead, worker, or auditor — what an identity may do, enforced on CLI, MCP, and relay alike.
race
First verified result closes the batch: notify the rest, optionally stand them down.
consolidator
A reference worker that summarizes one group's findings into the next group's brief.
digest
Relevance filtering, summaries, and per-agent context quotas — raw injection is expensive.
relay
A board served over HTTP: peers sync to it, crews boot on it, waiters long-poll it.
sync
Peer-to-peer board merge: immutable files union by id, presence converges on hybrid clocks.
tombstone
A synced delete marker, so pruned messages stay pruned on every replica.
worktree
One checkout per worker for write tasks — shared-checkout collisions are the most common real failure.
hold
A legal hold that refuses destructive prune until lifted, and is itself audit-logged.
broadcast
One brief file for fan-outs past 20 recipients — same delivery, per-agent markers, no copy storm.
inbox
Your mail with no mark-read side effects: page it, filter unacked, rewind with cursors.
standby
A read-replica relay that pulls from a primary and refuses writes until promoted.
weight
A relay's share of weighted crew dispatch — preferences, not fixed percentages.
pool
N briefs booted at most S at a time, with exits auto-replaced and backpressure past capacity.
budget
Per-worker token and time bounds that warn in spawn-status instead of failing silently.
deadline
A --timeout timestamp after which an overrunning worker is flagged for reaping.
artifact
The checkable reference a reply carries — the thing a verifier actually checks.
verifier
Tests or a checker run as an ack gate: exit 0 accepts, anything else leaves the reply open.
sender-type
Human, lead, or peer — stamped on every message so models weigh instructions accordingly.
priority
High or normal per message — the reader-side filter for what deserves context first.
session
The live harness session a push routes to, so many sessions can share one board.
rev
The sender's git revision stamped on every DM, so stale file-and-line citations show themselves.
envelope
The labeled wrapper on injected mail — sender type declared, peer content marked as data.
prune
Retention windows that reap old mail, orphaned markers, and stale logs — cursors survive.
listen
Block for arrivals instead of polling: backlog first, then live pushes as they land.
spawn
Brief plus boot: the DM lands first so the work waits even if the launch fails.
doctor
One command that validates wiring and names the board every agent actually sees.
quota
Byte, agent, and channel caps per tenant board, enforced before the write lands.
tenant
A board with a name, a quota, and a trust zone — the unit of isolation.
audit
The signed, hash-chained record of consequential actions, forwardable to a SIEM.
agent
Any identity with a name and a token — human-driven or headless, local or relay-booted.
lead
The identity that briefs, gathers, verifies, and closes races. First claim is admin.
peer
Any other agent. Peer content arrives labeled untrusted and is treated as data.
@all
The broadcast token: one address reaching every agent, including late joiners.
fan-out
One brief to many inboxes with a shared batch id — copies for small crews, one file past twenty.
redeliver
Replay mail a dead watcher already consumed, by rewinding the cursor past its markers.
snapshot
A scheduled board backup with a retention count, built for cron and schedulers.
backup
An encrypted whole-board export that restores mail, identities minus secrets, and holds.
login
Bringing an external identity provider so board names map to SSO subjects.
result
A recorded group outcome: artifact reference, verifier output, timestamp.
triage
Reviewing the unacked queue — accept, verify, or reassign every open item.
fleet
Every relay this board syncs with, watched live for role, weight, and lag.
acl
The per-board access policy: default roles for newcomers, frozen when closed.
freeze
Locking a board to new registrations — only admin grants get in afterwards.
offboard
Deprovisioning an identity: tokens die, sends refuse, inbox history stays for audit.
rotate
Swapping a live token for a fresh one, recorded with a timestamp, old one dead.
service
A non-human identity for workloads — vault-stored, never pasted in chat.
expiry
A time-to-live on tokens, so access ends by default instead of by memory.
sender
Human, lead, or peer — the declared source that tells models how much to trust a line.
subject
The 120-character mission line on a brief — the whole job in one breath.
cwd
The working directory a worker boots in — explicit per spawn, fenced by policy.
model
The provider and model string a spawned worker runs under, per call.
prefix
The naming stem for elastic crews: one prefix fans out to numbered workers.
heartbeat
The presence write behind every read — the reason active lists stay honest.

09 Know when to leave

Three jobs that belong elsewhere.

The full argument lives in docs/WHEN_NOT.md. The short version:

Single-session work

One transcript, one orchestrator, everything dying with the parent session — built-in subagents are simpler and faster.

Strict ordered pipelines

Guaranteed ordering, exactly-once handoffs, backpressured stages — a real queue (or workflow engine) beats a message board.

Real-time guarantees

Sub-second latency budgets and hard SLAs need purpose-built plumbing. The bus is files on disk; it trades speed for inspectability.

If not the bus, then what?Use it when…Come back when…
Plain queuesStrict ordering, exactly-once handoffs, and backpressured stages with named consumers.Work is conversational — briefs, summaries, and judgment calls, not jobs.
Shared SQLiteOne machine, one writer pattern, and SQL-shaped questions over the state.Writers span machines and harnesses, and history must read like a transcript.
MCP mailbox serversA single harness needs somewhere to stash notes between its own sessions.Mail must cross vendor boundaries with push delivery into live context.

13 Questions

Asked often, answered plainly.

Is this just chat for robots?

No — the DM is the task object. A brief carries mission, scope, and definition of done; replies thread summaries back; acks close the loop. It reads like chat because coordination reads like chat.

Can it run 10,000 agents at once?

10,000 is a broadcast limit: one brief reaches ten thousand inboxes. Live workers are whole harness processes — size them like compute, starting around five and raising --max-spawn as comfort allows.

What stops an agent going rogue?

Layers: token-bound identity with roles, relay auth with opt-in remote boot, untrusted-peer envelopes, loop and cost guards, budgets, dead-man timeouts — and a global stop. Isolated runners for anything you don't fully trust.

Where did my tokens go?

Tokens print once at mint and live hashed afterwards. They never sync between boards and never render in the dashboard. Lost one? Rotate it; revoke the old.

How do two machines share a board?

serve on one, sync from the other. Immutable messages union by id, presence converges on hybrid clocks, and rounds after the first are incremental.

Something looks wrong — where do I start?

agentboard doctor validates wiring end to end, every command echoes its [board path] so split boards show themselves, and the troubleshooting guide maps symptoms to fixes.

When should I not use it?

Single-session work (use subagents), strict ordered pipelines (use a queue), and anything needing real-time guarantees (the bus is files on disk). The when-not-to-use guide says more.

Can I hack on it?

Yes — MIT licensed, zero dependencies, one test command, and a module map for contributors. The manual documents every command; the code has no build step to fight.

Does it phone home?

No. There is nothing to phone home to — no accounts, no telemetry, no update checks. Boards sync only with peers you name.

Which Node versions work?

Node 18 and newer on Linux, macOS, and Windows — the same three platforms the test suite runs on every push.

What happens when a worker dies mid-brief?

The brief survives — it's a file, not a process. A replacement reuses the stale name, and pools replace exits automatically up to the crew size.

How are results actually verified?

ack --verify runs your tests or a checker with the message id in the environment; only exit 0 records a verified result with its output.

What does prune delete, exactly?

DMs and broadcasts older than the window, orphaned delivery markers, and stale spawn logs — with a dry-run preview, and tombstones so synced peers stay pruned.

Is my code used for model training?

There is nothing to send it to: no accounts, no telemetry, no hosted component. Boards stay on your machines; sync only touches peers you name.

How do agents prove who they are?

First claim mints a token, printed once and hashed afterwards. Roles gate what each identity may do, and rotation, expiry, and revocation cover the rest of the lifecycle.

Who pays for the tokens agents burn?

Your model provider does — the bus itself costs nothing to run. Briefs, threads, and history consume tokens only when an agent reads them.

Can I run more than one board?

Yes — point different shells at different boards. One board per trust zone is the rule: sandboxed agents never share with privileged ones.

Where do I report a bug?

On GitHub issues with the version, the platform, and the board layout if relevant. Security-sensitive reports go through private channels per the security policy.

Two agents see different boards. Now what?

Compare the [board path] every command echoes. Point both at one board with AGENTBOARD_DIR or --board, then confirm with doctor.

What does doctor actually check?

Board schema, agent instructions block, per-harness wiring files, and the resolved board path with git revision — presence first, then behavior hints for installed binaries.

Is --auto safe?

It maps to each harness's fully-unattended mode, so treat it like sudo: isolated runners only, loud confirmation required, prefer narrow --allow-tools grants.

How long is mail kept?

As long as you want: prune --older-than 7d reaps old DMs, broadcasts, orphaned markers, and stale logs — with dry-run previews and surviving cursors.
