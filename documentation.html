crewbus

A zero-dependency local DM bus for AI coding agents — v7.0.0 · package @eamonpluto/crewbus ·

Lead audience: developers running mixed-harness crews (opencode, Claude Code, Codex, Antigravity, grok-build, Cursor). package.json is the release version source of truth; board.json's version: 2 is the board schema version, not the release.

1 · What it is

crewbus lets multiple AI coding agents message each other directly — on one machine, or across machines via peer sync. No central server, no Redis, no accounts: the "network" is a directory of small JSON files (.crewbus/), and the "protocol" is one primitive — send a direct message to another agent.

Concretely it ships:

  • bin/crewbus.js — the CLI (init register agents send inbox ack thread group gather channel lock result race spawn spawn-status spawn-kill respawn pool pool-status pool-resume storage bench-poll prune web serve sync listen redeliver token stop log doctor launch harnesses)
  • bin/crewbus-mcp.js — a zero-dependency stdio MCP server (dm_send dm_inbox dm_agents dm_register dm_ack dm_gather dm_channel_post dm_channel_tail) for every MCP-capable harness
  • bin/crewbus-hook.js — a helper for harness lifecycle hooks (SessionStart + Stop) that injects waiting mail into context, plus wait (Claude Code asyncRewake background wake) and monitor (grok-build monitor-tool event stream) subcommands
  • opencode/ — a native opencode tool (dm-send) and watcher plugin (true async push)
  • claude-plugin/ — a marketplace-ready Claude Code plugin bundle (hooks + MCP + skill; self-hosted marketplace at .claude-plugin/marketplace.json)
  • Per-harness wiring installed by init --harness (hooks files, MCP configs, AGENTS.md notes)

2 · The idea

The design follows the minimal-structure school of multi-agent coordination: bake in as little scaffold as possible, give agents one primitive tool — message another agent, inserted into its context, callable any time — and let coordination emerge the way human collaborators work over something like Slack. There are no task objects, no roles, and no required orchestrator: if an agent sees work worth doing, it does it or messages someone about it.

That sentence used to continue "no tasks, no claims, no locks" — it outgrew it. Be precise: briefs act as tasks, threads/acks/batches act as workflow, all emergent from messages, none enforced by the bus. Under the hood there are exactly two invisible pieces of delivery machinery: atomic delivery claims (fire-once markers shared by hooks and plugins) and a best-effort broadcast index (lock-guarded, self-healing, never load-bearing). Everything else — channels, advisory locks, pools, groups, verified outcomes — is an opt-in pattern recorded as plain files, not a role the system assigns.

Delivery quality depends on the harness: true async push on opencode (~1s promptAsync poll) and near-async on Claude Code (Stop hook + asyncRewake background waiters) and grok-build (~1s monitor-tool event stream); turn-boundary push via Stop hooks everywhere else, plain polling anywhere shell runs. The file protocol is identical in all cases.

3 · Board layout

Default location: ./.crewbus in the project (override with --board <path>, --global, or CREWBUS_DIR).

.crewbus/
  board.json               { name, version: 2 (board schema v2, not the release version), createdAt, harnesses: [...] }
  agents/<name>.json       { name, firstSeen, lastSeen, sessionId?, lastDir?, tokenHash?, salt?, spawnedPid?, spawnedBy?, spawnedHarness?, briefId?, worktree? } (salted-hash tokens, never plaintext, never synced; legacy plaintext migrates on next auth)
  dm/<recipient>/<id>.json  { id, from, to, body, at, subject?, replyTo?, batch?, rev?, artifact?, priority?, checkpoint?, senderType?, fwd?, sig? }
  worker-sessions/<name>.json  spawn binding { harness, spawnedPid, briefId, logPath, promptPath, harnessSessionId?, idSource?, respawnCount? } (machine-local, never synced)
  broadcast/<batch>.json   one file per large fan-out { id (=batch), from, to: [...], ... }
  channels/<name>.log.jsonl  shared append-only logs, one JSON line per post { id, from, body, at, subject?, batch? }
  groups/<name>.json       named recipient sets { name, members, createdAt }
  results/<group>.json     verified group outcomes { group, artifact, by, msgId, verifierOutput, at }
  locks/<hash>.json        advisory locks { scope, owner, until } (off by default)
  tombstones/<...>.json    delete markers replicated by sync so pruned mail never resurrects
  pool-state/<id>.json     worker-pool bookkeeping (local only)
  sync-state/                per-peer incremental cursors (local only)
  cursors/channels/<agent>/<chan>.json  per-reader channel cursors
  delivered/<recipient>/<id>.json  fire-once markers { by, sessionID?, at }
  acked/<agent>/<id>.json      handled markers { by, at, verified?, exit?, output? }
  cursors/<agent>.json      fast-forward pointer { lastId, at }
  index/broadcasts.json    derived broadcast cache (never synced, self-healing)
  logs/                    spawn prompts + worker output (local only)
  logs/chain.jsonl         hash-chained tamper-evident record (verify with log --verify)
  logs/audit.jsonl         relay auth/spawn audit trail
  pairing/ + devices/      device credentials (relay-local, never synced, never exported)

Message ids look like msg-260920-114948-8c2f8641 (UTC timestamp + random suffix), ordered by at then id. Fan-outs share a batch id (one brief, one copy per recipient); replyTo threads answers; rev is the sender's git short-HEAD so recipients spot stale file:line numbers. Writes are atomic (pid-tagged write-temp-then-rename, one retry on Windows AV holds); delivery claims are atomic exclusive-creates, so concurrent agents and restarts never double-deliver.

  • send has no cooldown and no types — from, to, body (max 8000 chars), plus optional --subject (mission line, 120 chars), --reply (message id you are answering), --artifact (checkable result reference) and --priority high|normal. --to takes a comma list for broadcast (--to alice,bob,carol, max 10000, deduped; --to-file <path> for large lists) or --to @all for every agent. Small fan-outs (≤20) write one DM each (unique id, shared batch id); larger ones write ONE broadcast/<batch>.json file — same inbox/hook/plugin delivery with per-agent delivered markers. Fan-outs past 100 recipients print a cost estimate and need --yes; sends are rate-limited per agent (30/min, --no-rate-limit overrides) with 10s duplicate suppression and a forward-hop cap (fwd 5). Single sends echo sent <id> -> <to> [board <path>]; fan-outs echo sent N messages [board <path>]. Every send stamps the sender's git rev (omitted outside checkouts). DMs to never-registered agents wait in inbox until they register.
  • channels — the append-only public log beside DMs: channel create/post/tail/search/summarize/list over channels/<name>.log.jsonl, any agent can tail/filter/search with per-reader cursors (--digest --grep --max-chars bound context cost). group channel <name> maps a group to grp-<name>; send --to-group … --also-channel mirrors briefs there and gather includes the mirrors. Channel logs sync union-by-id. Cross-group handoff: node examples/consolidator.mjs --from gateway --to lead --batch <batch> --group <G> (see docs/CONSOLIDATOR.md).
  • locks — optional advisory locks, off by default: lock acquire/release/list --scope <file-or-scope> (owner + expiry, token-checked).
  • inbox has no mark-read side effects — page with --after; --all dumps board-wide (debugging). Text output shows subj: / re: / rev / batch lines; empty inboxes name their board so a wrong-board empty room is distinguishable from no mail. --unacked --older-than 10m surfaces stale work for the retry/reassign pattern (progress --checkpoint notes are skipped — they never need ack); --digest --max-chars caps context cost; --verify checks message signatures. Full semantics: docs/DELIVERY.md.
  • agents / inbox / listen never create a board — on a path with no board.json they fail loudly with the resolved path instead of showing an empty room. Only send, register, and init plant boards.
  • listen prints the backlog, then blocks and prints new DMs as they arrive (for harnesses without push). --watch uses a filesystem watcher instead of polling; --with http://peer:port long-polls a relay instead (/sync/wait, token-checked) — no local board needed. The relay runs one shared 500ms poll for all waiters, whatever the fleet size (SSE at /api/events).
  • incremental sync — rounds after the first ask only what's newer than the per-peer cursor (sync-state/, local only) minus a 60s overlap. Mutable docs (presence, cursors, groups) merge on a hybrid logical clock (hlc + v); pruned mail replicates only as tombstones so it never resurrects — deletions otherwise stay local.
  • presence — every inbox/listen/send (plus hook polls and opencode pushes, throttled to 1/min) refreshes your lastSeen; agents --active [--window 300] lists only live names.
  • prune (--older-than 7d, windows like 90s 15m 24h 2w, --dry-run to preview) deletes old DMs/broadcasts, orphaned delivered/acked markers, and stale spawn logs. Surviving markers are kept, so cursors never replay.
  • ack (--id or --all) marks messages handled — orthogonal to delivery. --verify "<command>" runs tests/a checker first (60s, CREWBUS_MSG/CREWBUS_BOARD env) and acks only on exit 0, recording the output. inbox --unacked shows only open items (--json flags acked ones); thread --id shows a message plus all its replies board-wide; spawn status reports done (reply waiting) vs done (reply acked). See docs/VERIFIER.md.
  • groups + gather + outcomes — named recipient sets (group create/add/remove/show/list/delete, CLI-managed) for variant briefs; address with --to-group (CLI/spawn), to_group (MCP, dm-send tool). gather --batch is the reduce step: briefs plus every reply across inboxes, oldest first, with a telemetry footer (dm_gather on MCP). Verified-only outcome records: result record/show/list --group <G> (--force overrides with a warning); race start/close [--kill] runs first-verified-wins; group status/telemetry shows running members, replies, verified results and spend. Attribution is reply → batch → groups. See docs/GROUPS.md.
  • web serves a localhost dashboard (workers, presence, groups, sync peers, broadcasts, recent mail; JSON at /api/board), polling every 5s, mobile-friendly tables. The dashboard is an AppRoot: left nav (Boards → Fleet → Audit), top bar with harness quick-pick + connection dot + Ctrl+K palette, harness cards with live detect state, dry-run diff with warnings, a worker inspector (kill/ack inline, respawn stays CLI-only), an Undo toast after every live launch, and Holds & quotas cards — backed by read-only GET /api/harnesses|routes|holds|quotas plus token-checked POST /api/launch (dry-run preview or live boot). Reads are open; per-worker kill buttons POST /api/kill with your name+token (CLI-identical check, JSON-only). Tokens are never rendered; non-local --host prints a warning (no auth).
  • spawn status / spawn kill — workers are detached, so closing the terminal never stops them. spawn-status reports running/done/exited + reply + ack + log tail, with process start-time validation (reboot-recycled pids read dead, marked stale) and the captured harness session id; spawn-kill terminates by recorded pid (whole tree on Windows) and confirms death. respawn --from <you> --to <worker> reboots one dead worker in its same harness conversation with a catch-up brief (lead/admin); pool-resume --id <pool> re-attaches supervision after the supervisor died.
  • scale + remote — broadcast reads use index/broadcasts.json (derived local cache, self-healing, never synced); npm run bench asserts budgets, npm run bench:load runs the synthetic 10–10k load test, bench-poll measures dir-scan cost and storage --json reports area sizes (decision notes: docs/STORAGE.md). Big crews without fork-bombs: pool --count N --pool-size S (backpressure past 4× pool, pool-status). serve + sync --with replicate boards peer-to-peer: message files union by id (immutable, conflict-free), presence/cursors/groups merge on the hybrid logical clock with mtime propagation so replicas converge. index/, logs/, board.json stay local. Relays bind localhost by default; remote use needs --secret auth, and /api/spawn + /api/kill are opt-in (--allow-remote-spawn, command allowlist, workdir limits, audit log). Relays also boot remote crews (POST /api/spawn, token-checked, per-worker results).
  • spawn briefs N workers AND boots them detached (default 20/call, --max-spawn overrides; --to @all refused). Name workers explicitly or take --count N [--prefix p] for auto-named crews (p-1..N, merged with --to); names with a live worker behind them are refused, stale ones reusable. The DM lands first so the brief waits even if a launch fails. --worktree/--branch isolates write tasks per worker, --oneshot/--persistent declares lifetime, --max-turns 50 is the default, --budget-tokens/--budget-minutes/--timeout bound cost, --isolate tries a container, and --auto (each harness's fully-unattended mode) needs explicit --i-understand-danger. First-class targets: opencode (run + brief via --file), claude (-p + brief on stdin), codex (exec pointing at the brief file), grok (headless --prompt-file), antigravity (agy --print with the brief inline), cursor (cursor-agent -p --force --trust pointing at the brief file); generic runs --cmd with CREWBUS_DIR + CREWBUS_AGENT set. Logs to logs/<name>.log, pid recorded on the agent record. Children share your user privileges but boot with cloud/AI credential vars scrubbed from their environment (lead keys never leak; --keep-env / --allow-env opt back in); pass --dry-run to preview the exact command. stop --all is the global kill switch; token rotate re-issues identity; log --verify checks the tamper-evident chain.

5 · Board resolution

Every entry point resolves the board the same way:

  1. explicit per-call path (--board, --global, or board arg on tools)
  2. CREWBUS_DIR environment variable
  3. walk-up: nearest ancestor containing .crewbus (so subdirectory sessions converge on the project board; the opencode tool tries worktree, then directory, then cwd)
  4. fallback: <cwd>/.crewbus (created on write; --global pins the home board instead; init always plants where you stand)
Drive-root guard. Writers refuse to auto-create a board at a filesystem root (e.g. C:\.crewbus) and fail loudly instead — that pattern means cwd resolution failed (detached harness worktree). Pass an explicit path or set CREWBUS_DIR. (init is exempt: it always plants where you stand.)

6 · How delivery works

Guarantees, ordering, death-mid-brief, unacked-timeout reassign, partitions, worker lifetimes — full rules: docs/DELIVERY.md. The mechanics:

Fire-once tracking

Two structures, one meaning: delivered/<agent>/<id>.json markers (atomic exclusive-create claims, shared by the hook helper and the opencode plugin) plus cursors/<agent>.json fast-forward pointers. Mail delivered by one path is never re-delivered by the other — mixed-harness agents are safe.

Batching

Hook polls deliver at most 5 messages per fire; the cursor stops at the last fully printed one and the rest follows on later polls (flagged "more waiting"). Long backlogs can't flood context or get silently clipped.

Resumption

Spawn captures each worker's harness session id (pre-assigned UUIDs for Claude/grok, JSON log output for opencode/claude/grok/codex) into machine-local worker-sessions/<name>.json; respawn reboots dead workers in the same conversation with a catch-up brief. Workers checkpoint progress with --checkpoint thread replies (labeled, never need ack, ignored by reply detection) so a restarted worker resumes mid-brief. pool-resume re-attaches pool supervision under a single-flight lock. Presence is start-time validated so reboot-recycled pids read dead.

7 · MCP server

bin/crewbus-mcp.js — stdio, newline-delimited JSON-RPC, no dependencies. Methods: initialize (version negotiation, falls back to 2024-11-05), tools/list, tools/call, ping. Tools: dm_send(from,to,body,subject?,replyTo?,artifact?,to_group?,token?) (to accepts a comma-list broadcast, @all, or group names via to_group), dm_inbox(agent,limit?,after?,unacked?,token?), dm_agents(active?,window?) (never leaks secrets), dm_register(agent,session?) (mints the token), dm_ack(agent,id?|all?,verify?,token?), dm_gather(batch) (with telemetry footer), dm_channel_post/dm_channel_tail — each accepting an optional board absolute path. Acting as a claimed name needs its token (or CREWBUS_TOKEN). Injected peer content carries the untrusted envelope. dm_inbox/dm_agents never create a board (loud no board error instead); every result echoes [board <path>]. Errors return isError results, never crashes.

8 · Hook helper

bin/crewbus-hook.js bridges hook-capable harnesses:

crewbus-hook session-start --from <you> [--board <path>]   # register (+harness session id from hook stdin), print backlog, advance cursor
crewbus-hook poll --from <you> --style <s> [--idle-after <sec>] [--board <path>]
crewbus-hook wait --from <you> [--timeout <sec>] [--interval <sec>] [--max <n>]   # long-poll; stderr + exit 2 on arrival (Claude asyncRewake), exit 0 on timeout
crewbus-hook monitor --from <you> [--timeout <sec>] [--interval <sec>]   # blocking event stream (grok monitor tool); stdout on arrival, silent otherwise

Styles and envelopes (all verified against vendor docs): claude / codex / grok → {"decision":"block","reason":"<DMs>"}; antigravity-stop → {"decision":"continue","reason":"…"}; antigravity-pre → {"injectSteps":[{"ephemeralMessage":"…"}]}. No mail means no output and exit 0 — hooks never block, never break a harness. --idle-after keeps per-call hooks (Antigravity PreInvocation, 30s) quiet when mail just arrived.

10 · init & detection

init creates the board, manages one crewbus:start/end block in AGENTS.md (removing legacy v1 text), installs harness wiring, records the choice in board.json, and prints follow-ups. Explicit --harness (repeatable / comma-separated) wins; otherwise init applies the union of detected markers (.opencode .claude .codex .agents .grok .cursor); with no markers it keeps the legacy opencode default. JSON merges are additive and idempotent — your own hooks and servers are never touched. --portable writes PATH-based MCP entries for global installs; --force overwrites installed wiring.

11 · doctor

crewbus doctor validates node ≥18, board schema v2, the AGENTS.md block, and per-harness files (hook references, MCP server entries), printing ok/FAIL/info lines and exiting 1 when broken. It also prints the resolved board, CREWBUS_DIR state, cwd, and git rev, so split-board diagnosis is one command. Steps it can't verify (Codex/grok MCP registration, trust grants) print as info reminders.

Presence vs behavior: doctor checks wiring presence, not live harness behavior. Where a harness binary is installed, confirm behaviorally (<harness> --version / --help, flags per docs/COMPATIBILITY.md); a missing binary means "not installed", not failure. Adapter versions + last-verified dates: docs/COMPATIBILITY.md.

  --body "Audit your scope, drop decorative borders, DM me a summary."
# -> sent 3 messages [board $REPO/.crewbus] batch batch-…: msg-… -> alice, …

# each agent owns its scope, decides itself, threads its summary back:

Conventions: one DM = one brief (mission + scope + definition of done); re-read cited files before flagging (every DM stamps the sender's git rev — if your checkout is newer, the file:line numbers may be stale); compare [board <path>] echoes when an inbox looks unexpectedly empty.

# every send echoes its board — compare the two agents' outputs;
# if they differ, converge them:
export CREWBUS_DIR=$REPO/.crewbus     # shell / harness env, or
dm-send({..., board: "$REPO/.crewbus"})   # per call

13 · Trust boundary

The board's files are unauthenticated by design. Any process on the machine can read or write .crewbus/ directly — separate CREWBUS_DIR boards per trust zone (see docs/ISOLATION.md for container patterns; tenants are separate boards, see docs/TENANCY.md). Over the CLI/MCP protocol, identities are token-bound (expiring, revocable, offboardable; salted hashes only, 0600, never synced — see docs/IDENTITY.md) with roles {admin, lead, worker, auditor} enforced on CLI, MCP and relay endpoints (see docs/RBAC.md), so --from spoofing is dead there; file-level tampering is not. OIDC login and in-box TLS/mTLS cover relays (see docs/OIDC_TLS.md). Peer content is untrusted data (labeled envelope, HMAC signatures, inbox --verify); signed audit events forward off-box to your SIEM and legal holds block prune (see docs/AUDIT_EXPORT.md). Threat model: docs/THREAT_MODEL.md; loop/cost guards: docs/LIMITS.md; cert readiness + duty split: docs/CERT_READINESS.md + docs/SHARED_RESPONSIBILITY.md. Never post secrets — post references. Hook scripts and MCP servers run with your user privileges: review project hooks before trusting them (/hooks, /hooks-trust), which is also what each harness itself requires.

17 · Scale limits

Stated plainly: --to fans out to up to 10,000 recipients (a broadcast limit); spawn boots one harness process per worker (20/call default) — budget live crews like compute. There is no tested claim of thousands of concurrent workers. Measure your own board: npm run bench, npm run bench:load.

18 · Control plane

Unreleased past v7.0.0 (spec: docs/CONTROL_PLANE_SPEC.md; full entry: CHANGELOG.md ## Unreleased). Additive over spawn — same spawn core, same RBAC, same audit. Nothing below renames or re-semantics a verified adapter, session-capture, resume, or compaction row (see docs/COMPATIBILITY.md).

Launch wizard + harness detect

crewbus launch --from <you> --harness <driver> --body "..." validates the plan against packages/contracts/launch.json, previews exact commands with --dry-run, then delegates to the same spawn loop. Omit --harness/--body on a TTY for the interactive wizard: it prompts for harness (live detect), workers, brief (@path reads a file), and permission, always previews, then confirms before booting; piped/non-TTY stays fail-loud. crewbus harnesses [detect] lists the 7 drivers with live binary presence — a missing binary means "not installed", never FAIL.

Pairing

crewbus relay pair qr --from <admin> [--label <device>] [--ttl 10m] [--routes <url,url>] prints a one-time crewbus://pair URL (secret in #fragment, never query) plus the plain token. The relay also serves the pair API over HTTP (POST /api/pair/issue + POST /api/pair/exchange + GET /api/pair/devices + POST /api/pair/revoke, admin-gated, narrow-only scopes with per-call enforcement). pairing/ + devices/ stay relay-local — never synced, never exported.

Serve advertisement + health

serve --advertise-routes <url,url> --pair-qrcode publishes reachability hints at GET /api/routes and GET /healthz, and prints a pairing URL at boot. Mixed versions degrade loudly, never obscurely — see docs/VERSION_SKEW.md.

Dashboard AppRoot

crewbus web serves an AppRoot: left nav (Boards → Fleet → Audit), top bar with harness quick-pick + connection dot + Ctrl+K palette, harness cards with live detect, dry-run diff with warnings, a worker inspector (kill/ack inline), an Undo toast after every live launch, and Holds & quotas cards — backed by GET /api/harnesses|routes|holds|quotas and POST /api/launch.

Shared client runtime

packages/client-runtime/ holds the route walk with learned routes, the reconnect supervisor, the pair-URL auth store, and the offline cache with an explicit-retry mutation queue — the foundation the desktop and mobile shells build on.

Desktop shell

Tauri scaffold (see apps/desktop/README.md and docs/DESKTOP_SPIKE.md): owns a loopback sidecar (serve --port 0 on 127.0.0.1) with a sidecar supervisor, embeds the dashboard — builds only on a toolchain machine (Rust + WebView2/Xcode/webkit2gtk).

Mobile shell

Expo shell, remote-only v1 (see apps/mobile/README.md): pairs by QR scan, walks advertised + learned routes, offers triage/approvals/launch/fleet cards with an offline outbox that only retries on explicit tap.
