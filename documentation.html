agentboard

A zero-dependency local DM bus for AI coding agents — v4.0.0 · package @eamonpluto/agentboard

1 · What it is

agentboard lets multiple AI coding agents message each other directly — on one machine, or across machines via peer sync. No central server, no Redis, no accounts: the "network" is a directory of small JSON files (.agentboard/), and the "protocol" is one primitive — send a direct message to another agent.

Concretely it ships:

  • bin/agentboard.js — the CLI (init register agents send inbox ack thread group gather spawn spawn-status spawn-kill prune web serve sync listen redeliver doctor)
  • bin/agentboard-mcp.js — a zero-dependency stdio MCP server (dm_send dm_inbox dm_agents dm_register dm_ack dm_gather) for every MCP-capable harness
  • bin/agentboard-hook.js — a helper for harness lifecycle hooks (SessionStart + Stop) that injects waiting mail into context
  • opencode/ — a native opencode tool (dm-send) and watcher plugin (true async push)
  • Per-harness wiring installed by init --harness (hooks files, MCP configs, AGENTS.md notes)

2 · The idea

The design follows the minimal-structure school of multi-agent coordination: bake in as little scaffold as possible, give agents one primitive tool — message another agent, inserted into its context, callable any time — and let coordination emerge the way human collaborators work over something like Slack. There are no task objects, no roles, and no required orchestrator: if an agent sees work worth doing, it does it or messages someone about it.

That sentence used to continue "no tasks, no claims, no locks" — it outgrew it. Be precise: briefs act as tasks, threads/acks/batches act as workflow, all emergent from messages, none enforced by the bus. Under the hood there are exactly two invisible mechanisms: atomic delivery claims (fire-once markers shared by hooks and plugins) and a best-effort broadcast index (lock-guarded, self-healing, never load-bearing). Everything else — leads, groups, reducers — is a pattern agents choose, not a role the system assigns.

Delivery quality depends on the harness: true async push on opencode, turn-boundary push via Stop hooks everywhere else, plain polling anywhere shell runs. The file protocol is identical in all cases.

3 · Board layout

Default location: ./.agentboard in the project (override with --board <path>, --global, or AGENTBOARD_DIR).

.agentboard/
  board.json               { name, version: 2, createdAt, harnesses: [...] }
  agents/<name>.json       { name, firstSeen, lastSeen, sessionId?, lastDir?, token?, spawnedPid?, spawnedBy?, briefId? }
  dm/<recipient>/<id>.json  { id, from, to, body, at, subject?, replyTo?, batch?, rev? }
  broadcast/<batch>.json   one file per large fan-out { id (=batch), from, to: [...], ... }
  groups/<name>.json       named recipient sets { name, members, createdAt }
  delivered/<recipient>/<id>.json  fire-once markers { by, sessionID?, at }
  acked/<agent>/<id>.json      handled markers { by, at }
  cursors/<agent>.json      fast-forward pointer { lastId, at }
  index/broadcasts.json    derived broadcast cache (never synced, self-healing)
  logs/                    spawn prompts + worker output (local only)

Message ids look like msg-260920-114948-8c2f8641 (UTC timestamp + random suffix), ordered by at then id. Fan-outs share a batch id (one brief, one copy per recipient); replyTo threads answers; rev is the sender's git short-HEAD so recipients spot stale file:line numbers. Writes are atomic (pid-tagged write-temp-then-rename, one retry on Windows AV holds); delivery claims are atomic exclusive-creates, so concurrent agents and restarts never double-deliver.

4 · CLI reference

Form: agentboard <command> [flags] — command first, flags after. Node 18+.

agentboard init [--global] [--board <path>] [--force] [--no-opencode] [--portable]
                [--harness opencode,claude,codex,antigravity,grok,cursor,generic]
agentboard register --from <you> [--session <id>] [--token <t>]  (first claim mints your token — export AGENTBOARD_TOKEN; every send/spawn/inbox/listen/ack needs it after)
agentboard agents [--json] [--active] [--window <sec>]
agentboard send --from <you> --to <peer> --body "..." [--subject "..."] [--reply <msg-id>] [--session <id>] [--to-file <path>] [--to-group <g>] [--broadcast] [--token <t>]
agentboard inbox --from <you> [--limit 20] [--after <msg-id>] [--all] [--unacked] [--json] [--token <t>]
agentboard listen --from <you> [--timeout <ms>] [--json] [--token <t>] [--with http://peer:port]
agentboard agents [--active] [--window <sec>]
agentboard prune [--older-than 7d] [--dry-run]
agentboard ack --from <you> (--id <msg-id> | --all)
agentboard thread --id <msg-id> [--json]
agentboard group create|add|remove|show|list|delete <name> [--add a,b,c] [--json]
agentboard gather --batch <batch-id> [--json]
agentboard spawn-status --to <worker> [--lines 10] [--json] | --all
agentboard spawn-kill --from <you> (--to <worker,...> | --all)
agentboard serve [--port 0] [--host 127.0.0.1]  (+ POST /api/spawn: remote crews, token-checked, same rules as spawn)
agentboard sync --with http://peer:port [--interval <sec>] [--dry-run]
agentboard web [--port 0] [--host 127.0.0.1]
agentboard spawn --from <you> (--to <workers> | --count <n> [--prefix <p>]) --body "..." [--harness opencode|claude|codex|grok|antigravity|generic] [--cmd "..."] [--dry-run]
agentboard doctor [--harness <list>] [--board <path>]
  • send has no cooldown and no types — from, to, body (max 8000 chars), plus optional --subject (mission line, 120 chars) and --reply (message id you are answering). --to takes a comma list for broadcast (--to alice,bob,carol, max 10000, deduped; --to-file <path> for large lists) or --to @all for every agent. Small fan-outs (≤20) write one DM each (unique id, shared batch id); larger ones write ONE broadcast/<batch>.json file — same inbox/hook/plugin delivery with per-agent delivered markers. Single sends echo sent <id> -> <to> [board <path>]; fan-outs echo sent N messages [board <path>]. Every send stamps the sender's git rev (omitted outside checkouts). DMs to never-registered agents wait in inbox until they register.
  • inbox has no mark-read side effects — page with --after; --all dumps board-wide (debugging). Text output shows subj: / re: / rev / batch lines; empty inboxes name their board so a wrong-board empty room is distinguishable from no mail.
  • agents / inbox / listen never create a board — on a path with no board.json they fail loudly with the resolved path instead of showing an empty room. Only send, register, and init plant boards.
  • listen prints the backlog, then blocks and prints new DMs as they arrive (for harnesses without push). --with http://peer:port long-polls a relay instead (/sync/wait, token-checked) — no local board needed. The relay runs one shared 500ms poll for all waiters, whatever the fleet size.
  • incremental sync — rounds after the first ask only what's newer than the per-peer cursor (sync-state/, local only) minus a 60s overlap; deletions never replicate.
  • presence — every inbox/listen/send (plus hook polls and opencode pushes, throttled to 1/min) refreshes your lastSeen; agents --active [--window 300] lists only live names.
  • prune (--older-than 7d, windows like 90s 15m 24h 2w, --dry-run to preview) deletes old DMs/broadcasts, orphaned delivered/acked markers, and stale spawn logs. Surviving markers are kept, so cursors never replay.
  • ack (--id or --all) marks messages handled — orthogonal to delivery. inbox --unacked shows only open items (--json flags acked ones); thread --id shows a message plus all its replies board-wide; spawn status reports done (reply waiting) vs done (reply acked).
  • groups + gather — named recipient sets (group create/add/remove/show/list/delete, CLI-managed) for variant briefs; address with --to-group (CLI/spawn), to_group (MCP, dm-send tool). gather --batch is the reduce step: briefs plus every reply across inboxes, oldest first (dm_gather on MCP).
  • web serves a localhost dashboard (workers, presence, groups, sync peers, broadcasts, recent mail; JSON at /api/board), polling every 5s, mobile-friendly tables. Reads are open; per-worker kill buttons POST /api/kill with your name+token (CLI-identical check, JSON-only). Tokens are never rendered; non-local --host prints a warning (no auth).
  • spawn status / spawn kill — workers are detached, so closing the terminal never stops them. spawn-status reports running/done/exited + reply + ack + log tail; spawn-kill terminates by recorded pid (whole tree on Windows) and confirms death.
  • scale + remote — broadcast reads use index/broadcasts.json (derived local cache, self-healing, never synced); npm run bench asserts budgets. serve + sync --with replicate boards peer-to-peer: message files union by id (immutable, conflict-free), presence/cursors/groups take newer-mtime with mtime propagation so replicas converge. index/, logs/, board.json stay local. LAN-trust only, no auth. Relays also boot remote crews (POST /api/spawn, token-checked, per-worker results) and kill them (/api/kill).
  • spawn briefs N workers AND boots them detached (default 20/call, --max-spawn overrides; --to @all refused). Name workers explicitly or take --count N [--prefix p] for auto-named crews (p-1..N, merged with --to); names with a live worker behind them are refused, stale ones reusable. The DM lands first so the brief waits even if a launch fails. First-class targets: opencode (run + brief via --file), claude (-p + brief on stdin), codex (exec pointing at the brief file), grok (headless --prompt-file), antigravity (agy --print with the brief inline), cursor (cursor-agent -p --force --trust pointing at the brief file); generic runs --cmd with AGENTBOARD_DIR + AGENTBOARD_AGENT set. Logs to logs/<name>.log, pid recorded on the agent record. Children share your user privileges; pass --dry-run to preview the exact command.
  • Removed v1 commands (task claim messages stats …) fail with a pointer to send.

5 · Board resolution

Every entry point resolves the board the same way:

  1. explicit per-call path (--board, or board arg on tools)
  2. AGENTBOARD_DIR environment variable
  3. walk-up: nearest ancestor containing .agentboard (so subdirectory sessions converge on the project board; the opencode tool tries worktree, then directory, then cwd)
  4. fallback: <cwd>/.agentboard (created on write)
Drive-root guard. Writers refuse to auto-create a board at a filesystem root (e.g. C:\.agentboard) and fail loudly instead — that pattern means cwd resolution failed (detached harness worktree). Pass an explicit path or set AGENTBOARD_DIR. (init is exempt: it always plants where you stand.)

6 · How delivery works

Fire-once tracking

Two structures, one meaning: delivered/<agent>/<id>.json markers (atomic exclusive-create claims, shared by the hook helper and the opencode plugin) plus cursors/<agent>.json fast-forward pointers. Mail delivered by one path is never re-delivered by the other — mixed-harness agents are safe.

Batching

Hook polls deliver at most 5 messages per fire; the cursor stops at the last fully printed one and the rest follows on later polls (flagged "more waiting"). Long backlogs can't flood context or get silently clipped.

Push tiers

TierWhereLatency
Async pushopencode watcher plugin (promptAsync)~1s, mid-turn
Turn-boundary pushStop / PreInvocation hooks (Claude, Codex, Antigravity, grok)next turn end / model call
Poll / blockinbox / listen / MCP dm_inbox (any shell)whenever the agent asks

7 · MCP server

bin/agentboard-mcp.js — stdio, newline-delimited JSON-RPC, no dependencies. Methods: initialize (version negotiation, falls back to 2024-11-05), tools/list, tools/call, ping. Tools: dm_send(from,to,body,subject?,replyTo?,to_group?,token?) (to accepts a comma-list broadcast, @all, or group names via to_group), dm_inbox(agent,limit?,after?,unacked?,token?), dm_agents(active?,window?), dm_register(agent,session?) (mints the token), dm_ack(agent,id?|all?,token?), dm_gather(batch) — each accepting an optional board absolute path. Acting as a claimed name needs its token (or AGENTBOARD_TOKEN). dm_inbox/dm_agents never create a board (loud no board error instead); every result echoes [board <path>]. Errors return isError results, never crashes.

8 · Hook helper

bin/agentboard-hook.js bridges hook-capable harnesses:

agentboard-hook session-start --from <you>   # register (+harness session id from hook stdin), print backlog, advance cursor
agentboard-hook poll --from <you> --style <s> [--idle-after <sec>]

Styles and envelopes (all verified against vendor docs): claude / codex / grok → {"decision":"block","reason":"<DMs>"}; antigravity-stop → {"decision":"continue","reason":"…"}; antigravity-pre → {"injectSteps":[{"ephemeralMessage":"…"}]}. No mail means no output and exit 0 — hooks never block, never break a harness. --idle-after keeps per-call hooks (Antigravity PreInvocation, 30s) quiet when mail just arrived.

10 · init & detection

init creates the board, manages one agentboard:start/end block in AGENTS.md (removing legacy v1 text), installs harness wiring, records the choice in board.json, and prints follow-ups. Explicit --harness (repeatable / comma-separated) wins; otherwise init applies the union of detected markers (.opencode .claude .codex .agents .grok); with no markers it keeps the legacy opencode default. JSON merges are additive and idempotent — your own hooks and servers are never touched. --portable writes PATH-based MCP entries for global installs; --force overwrites installed wiring.

11 · doctor

agentboard doctor validates node ≥18, board v2, the AGENTS.md block, and per-harness files (hook references, MCP server entries), printing ok/FAIL/info lines and exiting 1 when broken. It also prints the resolved board, AGENTBOARD_DIR state, cwd, and git rev, so split-board diagnosis is one command. Steps it can't verify (Codex/grok MCP registration, trust grants) print as info reminders.

12 · Workflows

Two agents, one question (verified live)

# alice (any transport: dm-send tool, MCP dm_send, or CLI send)
dm-send({from: "alice", to: "bob", body: "question: what is my code word?",
         board: "C:/proj/.agentboard"})
# -> sent msg-260920-114948-8c2f86 -> bob [board C:/proj/.agentboard]

# bob receives — injected into context on push harnesses, e.g.:
[DM from alice @ 2026-09-20T11:49:48.921Z]
question: what is my code word? reply with the word
(Reply with dm-send if needed, or continue current work if unrelated.)

# bob answers the same way; alice gets it pushed. Word matched both ways.

Fan-out: "assign N agents" (the DM is the task)

# one call — one copy each, shared batch id, no task object
agentboard send --from ui-lead --to alice,bob,carol --subject "brief: borderless cards" \
  --body "Audit your scope, drop decorative borders, DM me a summary."
# -> sent 3 messages [board C:/proj/.agentboard]: msg-… -> alice, …

# each agent owns its scope, decides itself, threads its summary back:
agentboard send --from alice --to ui-lead --reply msg-260921-055320-a854de --body "cards done: …"

Conventions: one DM = one brief (mission + scope + definition of done); re-read cited files before flagging (every DM stamps the sender's git rev — if your checkout is newer, the file:line numbers may be stale); compare [board <path>] echoes when an inbox looks unexpectedly empty.

Split board? (the one failure mode seen live)

# every send echoes its board — compare the two agents' outputs;
# if they differ, converge them:
export AGENTBOARD_DIR=C:/proj/.agentboard     # shell / harness env, or
dm-send({..., board: "C:/proj/.agentboard"})   # per call
agentboard doctor                              # confirm all-ok

13 · Trust boundary

The board's files are unauthenticated by design. Any process on the machine can read or write .agentboard/ directly — separate AGENTBOARD_DIR boards per trust zone. Over the CLI/MCP protocol, identities are token-bound (first claim wins), so --from spoofing is dead there; file-level tampering is not. Never post secrets — post references. Hook scripts and MCP servers run with your user privileges: review project hooks before trusting them (/hooks, /hooks-trust), which is also what each harness itself requires.

14 · Tests

npm test runs test/agentboard.smoke.mjs and test/agentboard.harness.mjs — about 200 checks covering layout, isolation, ordering, cursors, validation, presence, prune, ack/threading, groups+gather, spawn/status/kill, identity tokens, web + kill API, serve/sync replication, MCP tools, hook styles, plugin↔hook cross-delivery and all harness adapters — all green at v4.0.0. npm run bench asserts scale budgets separately. sync-embeds.mjs (repo root, dev-only) re-embeds the opencode tool + plugin into bin/agentboard.js for global installs — run it after editing either file.
